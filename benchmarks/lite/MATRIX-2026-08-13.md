## The failure, attributed: `line_count_invalid`, refused rather than repaired

Ledger rows for the failing cells carry `line_count_invalid` at attempt 2 with one repair - the
model picked a chassis whose MINIMUM line count exceeds what the brief carries, the repair
re-emitted a decision with the same fault, and the generation died. `validateLiteDecision` fires
it when the emitted line count falls outside the chosen chassis's `visibleFields` range.

Measured, free, with `retrieveLiteReferenceSet` on the failing brief (a 2-line brief: speaker
name + academic role):

```
5 of 11 lower-third references; mark-capable only (wordmark)
ls17 3-4   <- offered FIRST; its minimum is 3
lt25 1-2
ls12 2-3
lt02 1-2
lt37 2-4
```

`ls17` Lectern is the best semantic match for an academic brief and cannot legally hold it.

**This is NOT a regression from the P1 catalog work, and the check that says so is one line:**
the same brief WITHOUT a mark retrieves `ls17` first as well (`5 of 13 references`, no mark
narrowing). The exposure has always existed for markless briefs; drawing slots on the seven
chassis extended it to MARKED ones, which is why it had never been measured - before §3.6.2 a
marked request was confined to six chassis that all hold one or two lines.

**The shape of the defect is the one this plan has now written down three times:** a rule that
converts a bad graphic into NO graphic is worse than the defect it replaces. The mark repair
re-picks a chassis or paints a well; the palette repair re-maps, clamps and neutralizes; the line
count alone still refuses. The obvious fix is the same ladder - re-pick a chassis whose measured
capacity holds the lines the model emitted, and record it as an adjustment - and it is a change
to refusal semantics, so it is stated here rather than taken.

## The false start, and what it proves

The first attempt failed 8 of 8 cells and was stopped rather than run to completion (§4.2: two
prior paid rounds were mis-read as model failure when the platform was at fault). Root cause,
recorded by the ledger itself as `rejection_reason = ledger_update`: **the bench server writes to
the real Supabase ledger, and the endpoint now writes `ai_generations.adjustments`, a column
production does not have because migration 0043 is not applied.** Every generation 500'd on the
outcome write AFTER its model call was already billed.

That is exactly the deploy-order hazard §3.2 predicted, arriving through the bench rather than
through production, and it is worth keeping for three reasons:

- **It is proof the hazard is real**, not a theoretical note in a plan.
- **The eval's cost line reported $0.0000 for it** while the ledger booked ~$0.011. Failed rows'
  spend is uncounted (`scripts/ai-lite-eval.mjs` sums successful rows only) - so a round that
  fails wholesale reads as free, which is the worst possible time for that to be true.
- **The fix for the BENCH is `AI_LITE_EVAL_MEMORY_LEDGER=1`**, which is where bench rows belong
  anyway. The cost is attribution: `rejection_reason` then lives in memory rather than in SQL.
  The attribution above was read from the rows the broken run had already written.
